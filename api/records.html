Records

Records are the core objects in Dreamteam CRM. Contacts, companies, deals, meetings, notes, and tasks are all records, as is every custom object you define. These endpoints work the same way for each: you change the object type in the path, and the request and response shapes stay the same. The examples below use contacts, companies, and deals.

Some object types add their own rules or endpoints

The routes here cover every object type, and you create, edit, and delete each one the same way. A few types layer extra behaviour on top: tasks, for example, must be linked to a record and are handed over through a dedicated reassignment endpoint - see Tasks. Records of your own custom objects use these same routes with the custom object's slug in the path - see Custom objects.

The record model

A record has a stable numeric id, an object type it belongs to (like contact or deal), and a bag of properties whose shape depends on the object type. Optionally, a record can carry an associations block that embeds linked records grouped by type.

AI-generated fields live inside properties, next to the schema fields. Text-heavy ones are prefixed ai_ (e.g. ai_about, ai_exec_summary) and come back as a JSON string encoding a card - { "title", "icon_category", "content": [...], "metadata" } - which some fields return as an array. Scalar signals such as engagement, confidence, risk, and icp are plain values. All are read-only and populated asynchronously, so a freshly-created record returns them empty or absent.

Properties

AttributeDescription
idNumeric identifier for the record. Stable across the record's lifetime.
typeThe object type - contact, company, deal, meeting, note, or task, plus any custom object type you define.
propertiesObject of key-value pairs. Keys are property names from the object's schema; values match the property's data type.
ai_* read-onlyAI-generated fields, nested inside properties. Text fields (prefixed ai_) are JSON-string cards; scalar signals (e.g. engagement, icp, confidence) are plain values. Populated asynchronously - empty or absent on a new record.
associationsOptional. Present when the request opts into embedding. Grouped by object type, with a records array and per-type metadata.
created_atISO 8601 timestamp when the record was created.
updated_atISO 8601 timestamp of the last property change.
created_byUser id of the record's creator.

List records

GET /api/v1/objects/{object}/records

Lists the contacts, companies, deals, meetings or notes you have access to, a page at a time. Pass the object type in the URL path. Pass associations query parameters (repeatable) to embed linked records under each returned record's associations block. Omit them to get properties only.

Path parameters

object string · requiredObject type - one of contact, company, deal, meeting, note, task, or a custom object.

Query parameters

page integerPage number, starts at 1. Defaults to 1.
page_size integerRecords per page, up to 100. Defaults to 20.
associations string[]Object types to embed under each record. Repeatable - e.g. ?associations=company&associations=note. Omit to skip embedding.

Returns

A paginated list of records under results, plus a metadata object with page, page_size, total_elements, total_pages, has_next, and has_previous.

Create a record

POST /api/v1/objects/{object}/records

Creates a single record - pass the object type in the URL path. You can create the standard CRM record types contact, company, deal, note, and task, plus records of any custom object type. A note needs only its content (optional) and can be created with or without a linked record. The request body's properties object must satisfy that type's schema for required fields; unknown property keys are rejected. Some types are read-only through this API - recording records, for instance, are ingested by call and meeting integrations and reject direct creation.

Associations at create time

Link the new record to existing records by setting the object's lookup fields inside properties - there is no separate associations array. A lookup field is named <object>_ids and takes the target record id(s); a deal, for example, accepts company_ids and contact_ids. Call the Schema endpoint to see which lookup fields an object supports.

Naming heads-up: the lookup field you write (e.g. company_ids) maps to an association whose full identifier surfaces elsewhere as association_name (e.g. "company_deal_assoc"). To read a record's linked records back, pass the associations query parameter on Find Records or Retrieve.

Path parameters

object string · requiredObject type to create the record under.

Request body

properties object · requiredObject matching the target object's schema. Required fields must be present. To link related records, set the object's lookup fields here (e.g. company_ids, contact_ids).

Returns

The created record, including its assigned id, created_at, and created_by.

Object

Retrieve a record

GET /api/v1/objects/{object}/records/{id}

Fetches a single contact, company, deal, meeting, or note by its id. By default the sample request embeds linked company and contact records - omit the associations query params to get a plain record with only its properties.

Path parameters

object string · requiredObject type of the record.
id integer · requiredNumeric identifier of the record.

Query parameters

associations string[]Object types to embed under associations. Repeatable. Omit to skip embedding.

Returns

The record. If associations was requested, a matching associations block is embedded - grouped by object type, each with a records array and per-type metadata (total, has_more). Embedded associations return ids only - see Hydrate by IDs for turning them into full records.

Paging associations past 100

Embedded associations are capped at 100 per type. If has_more: true, paginate the rest with the dedicated endpoint:

GET /api/v1/objects/{object}/records/{id}/associations/{target_type}?page=1&page_size=50

Read-only. Writing new association links is not available yet.

Fetching note content

Notes come back as {id, association_name} pairs. To get the actual note text, call Retrieve a Record with object=note and the note's id.

Update a record

PATCH /api/v1/objects/{object}/records/{id}

Updates a record by merging the properties object in the request body into the record. Keys omitted from the body are left unchanged. Set a value to null to explicitly clear that field. Use Content-Type: application/merge-patch+json.

PATCH merges — the safe default

PATCH merges - only the fields you send change; everything else is left alone. Safe for partial updates.

About application/merge-patch+json: it's plain JSON with one rule the server enforces - only the keys you send actually change. Everything you leave out is untouched. Setting a value to null clears that field.

Path parameters

object string · requiredObject type of the record.
id integer · requiredNumeric identifier of the record.

Request body

properties object · requiredPartial property map. Keys present overwrite the record's current values; keys omitted are unchanged.

Returns

The updated record with its refreshed updated_at timestamp.

Delete a record

DELETE /api/v1/objects/{object}/records/{id}

Permanently deletes a record by id. On success the endpoint returns 204 No Content with an empty body - and it returns the same 204 even when no record with that id exists, so a delete is safe to repeat. The URL is the same as Retrieve and Update; only the object slug and id change.

Deleting is permanent

There is no recycle bin and no restore endpoint - a deleted record cannot be recovered through the API. Records that exist only inside the one you delete, such as its notes, are removed with it.

A company with deals can't be deleted

Deleting a company that still has one or more deals attached returns 409 Conflict. Delete or move those deals first, then delete the company. Deleting a contact or a deal is never blocked this way.

Path parameters

object string · requiredObject type of the record - contact, company, deal, note, task, or a custom object.
id integer · requiredNumeric identifier of the record to delete.

Returns

204 No Content with an empty response body - there is no JSON to parse, so check the status code. Deleting a contact or a deal always returns 204. The one error you can hit is on a company: 409 Conflict while it still has deals attached (see below).
